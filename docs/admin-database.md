# Content database (PostgreSQL 17)

**Source of truth for the architecture:** [`admin-architecture-approved.md`](admin-architecture-approved.md) §17 and review §C.
**Implemented in:** Phase B (content), Phase C (users, sessions, second factors, audit log; see [`admin-auth.md`](admin-auth.md)).
**Code:**
- `apps/api/src/db/schema.ts` (Drizzle);
- `apps/api/drizzle/` (committed SQL migrations);
- `apps/api/db/provision.sql` (roles);
- `apps/api/src/content/{import,export}.ts`.

---

## 1. Principles

| Rule | How |
|---|---|
| One record, one row per language | `<entity>` (language-independent) + `<entity>_translations` (PK `entity_id, locale`) |
| Stable IDs survive everything | UUIDv7 primary key (generated by the app) + `key` = the content-layer ID (`project-solbar-israel`), unique, never changed |
| Nothing disappears silently | Content relations are FKs with `ON DELETE RESTRICT`; translation and child rows `CASCADE` |
| No free-form JSON | JSONB only for ordered lists inside a translation and code-defined slot maps; every JSONB column has a Zod schema (`packages/core/src/content/jsonb.ts`) and the table has `schema_version` |
| The application cannot change the schema | Three roles (§3) |
| The site does not depend on the database | The site is built from an export (§5); a database outage never affects the live site |

**Phase F columns** (`drizzle/0004_translation_review.sql`, additive): the seven admin-managed entities (`pages`, `projects`, `technologies`, `products`, `epcm_stages`, `patents`, `videos`) have `source_revision` (revision of the English translatable text); their translation tables have `version`, `approved_source_revision`, `approved_by`, `edited_source_revision`. `settings_translations` is unchanged. See [`admin-translations.md`](admin-translations.md) §2.

**Phase G tables** (`drizzle/0005_publishing.sql`, additive; [`admin-publishing.md`](admin-publishing.md)):

| Table | Contents |
|---|---|
| `content_revisions` | one row per change of a translatable record: type, id, key, number (unique per record), kind, locale, source revision, entity version, title, full record `data` (`json`, key order kept), `summary`, author, time. `UPDATE` / `DELETE` / `TRUNCATE` revoked from the app role plus a trigger |
| `content_snapshots` | the published store of a release (`json`), sha256, revision number per record, translation summary. Append-only |
| `releases` | key, kind (`release`/`preview`), status, snapshot, previous release, version, attempt, note, validation (errors/warnings), failure, build times, heartbeat, artifact checksum/bytes/files/pages, activation. At most one `active` per kind (partial unique index); identity and artifact columns immutable (trigger); no `DELETE` |
| `release_events` | append-only history of every transition (from, to, event, actor, details) |
| `preview_grants` | release, user, session (cascade), sha256 of the one-time token and of the cookie, expiry, consumed / revoked times; no `DELETE` |

**Phase C tables** (`drizzle/0002_auth_users_sessions_audit.sql`, `0003_audit_append_only.sql`):

| Table | Contents |
|---|---|
| `users` | e-mail (unique, stored normalized: a CHECK enforces lower case and trimmed), name, `role` (enum of the 6 roles), `status` (`active`/`disabled`), Argon2id `password_hash`, failure counter, lock-out, `version`, audit columns |
| `sessions` | sha256 of the token (never the token), user, `aal` 1/2, `mfa_verified_at`, `mfa_failures`, created / last seen / expires, IP hash, User-Agent, `revoked_at` + reason |
| `known_devices` | sha256 of the device cookie, user, expiry (lock-out bypass for browsers that signed in before) |
| `webauthn_credentials` | credential ID (unique), public key (`bytea`), sign counter, transports, device type, backup flags, name, last used |
| `webauthn_challenges` | challenge (unique), purpose, session, user, expiry, `used_at` (single use) |
| `totp_credentials` | one per user: AES-256-GCM encrypted secret, confirmation time, last used time step (replay guard) |
| `recovery_codes` | sha256 of each code, `used_at` |
| `password_resets` | sha256 of the token, expiry, `used_at` |
| `audit_events` | append-only log (bigint identity): time, actor, action, resource, result, request ID, IP hash, User-Agent, `summary` jsonb, `schema_version` |

All translatable entities carry:
- `status` (`draft`/`published`/`archived`), `position`, `source_locale`;
- `version` (optimistic locking, used from Phase E);
- `published_at`, `archived_at`;
- `created/updated_at/_by`; since Phase C, `created_by` / `updated_by` are FKs to `users` (`ON DELETE RESTRICT`). The import leaves them `NULL`.

Each translation row carries `tr_status`, `approved_source_hash` and `approved_at`. They are `NULL` for the source language.

**Constraints worth knowing:**
- `UNIQUE (locale, slug)` per routable type.
- `patents.placements` ⊆ {home, registry}, at least one.
- `settings` is a singleton.
- Redirect `from` and `to` must be internal paths: they start with `/`, contain no `//`, no backslash and no control characters, and are not equal to each other. Status code is 301 or 302. This makes open redirects impossible at the database level (approved §11.3).

## 3. Roles (approved §17.1)

| Role | Rights | Used by |
|---|---|---|
| `soltex_migrate` | owns the database and schema | `npm run db:migrate` only (deploy step). Its password is not in the API environment |
| `soltex_app` | `SELECT, INSERT, UPDATE, DELETE` on content tables; read-only on `locales`; **no** `CREATE / ALTER / DROP / TRUNCATE` | API, worker, `db:import`, `db:export` |
| `soltex_backup` | `pg_read_all_data` | backup jobs (Phase N) |

- Provisioning (once per environment, as superuser): `apps/api/db/provision.sql`. Passwords are passed as psql variables, never committed.
- Default privileges make every future table created by `soltex_migrate` available to `soltex_app` through DML only.
- **`audit_events` is append-only:**
  - `soltex_app` has only `INSERT, SELECT` (migration 0003 revokes `UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER`);
  - a `BEFORE UPDATE OR DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger raise `insufficient_privilege` for **every** role, including the owner `soltex_migrate`;
  - `soltex_backup` can read but not write it;
  - `apps/api/src/db/db.test.ts` proves all of this.
- Correcting an audit entry is impossible by design. Retention (approved §19) will be a separately reviewed migration that drops whole partitions or rows older than the retention period. It is not part of Phase C.

## 4. Decisions

| # | Decision | Reason |
|---|---|---|
| DB-1 | **PostgreSQL 17**; the code uses nothing 17-specific (16–18 interchangeable) | Approved §17.3. Local tests ran on 17.10 |
| DB-2 | **UUIDv7 from the application** (`uuid` package) | PostgreSQL 17 has no built-in `uuidv7()`; time-ordered keys index well |
| DB-3 | **The slug lives in the translation row**, identical in all languages for now; export fails if languages differ | Localized slugs are DEFERRED but the model is ready (review §0) |
| DB-4 | **`page_translations.copy` is an ordered array `[{slot, text}]`**, not an object | `jsonb` does not preserve object key order; slot order is part of the stored content |
| DB-5 | **`page_list_items.structure` is `json`, not `jsonb`** | It is an arbitrary code-defined object whose key order matters (the export must reproduce the seed byte for byte). The translatable texts are in `page_list_item_translations.texts` (`jsonb`), keyed by path |
| DB-6 | **Fixed-shape JSONB objects are re-read through their Zod schema** | The schema restores the canonical key order (`label, value`, `title, description`, …) |
| DB-7 | **Media and redirects are exported sorted by key / source path** | They have no editorial order; the seed lists media by ID |
| DB-8 | **Import never deletes**: entities missing from the store are reported, not removed | Importing an old seed must never wipe content edited in the admin |
| DB-9 | **Translation status vocabulary kept from Phase 1** (`missing`, `in_progress`, `approved`) | Exact round trip; the admin maps them to Russian labels. Phase F derives `outdated` from source revisions instead of adding an enum value ([`admin-translations.md`](admin-translations.md) §1–2) |
| DB-10 | **Secrets are stored only as hashes or ciphertext:** session, device, reset tokens and recovery codes as sha256; TOTP secrets as AES-256-GCM bound to the user; IP addresses and unknown e-mails as keyed HMAC | A database dump does not allow signing in or tracking addresses (Phase C) |
| DB-11 | **The audit log is protected by triggers, not only grants** | Grants protect against the application; the trigger also protects against mistakes by the schema owner. Phase B migrations were not changed; the protection is a new migration (0003) |
| DB-12 | **Users are never hard-deleted**; they are disabled | Audit rows and `created_by` / `updated_by` reference them (`RESTRICT`) |

## 5. Import, export, build from the database

```
npm run db:migrate                                 # MIGRATION_DATABASE_URL
npm run db:import                                  # DATABASE_URL; default --seed apps/web/src/content/seed
npm run db:export -- --out <dir>                   # ten seed files
npm run db:export -- --file <store.json>           # one ContentStore file
CONTENT_SOURCE=file CONTENT_STORE_FILE=<store.json> npm run build:web
```

- **Import** runs in one transaction and is idempotent: entities are matched by `key`, translations upserted, ordered children replaced.
- **Export** reads one consistent snapshot (`REPEATABLE READ`, read-only) and writes exactly the seed format.

**Verified (Phase B):**
1. `seed → DB → export` is byte-identical to the 10 seed files.
2. The site built from the database export is byte-identical to the site built from the seed (229 files, 180 HTML).
3. A second import changes no row count and no exported byte.
4. A failing import rolls back completely.
5. Invalid list content is rejected by the Zod schemas.
6. The roles and constraints of §2–§3 hold: `apps/api/src/db/db.test.ts`, 9 tests (since Phase C, including the audit grants and trigger).

CI repeats all of this against a PostgreSQL 17 service container, plus a check that the committed migrations match the schema.

## 6. Local development database

Any PostgreSQL 17 works. On macOS the simplest options:
- **Postgres.app** (postgresapp.com, choose version 17);
- or Docker:
  ```
  docker run -d --name soltex-pg -p 5432:5432 -e POSTGRES_PASSWORD=<local superuser password> postgres:17
  ```

Then, once:

```
psql -h 127.0.0.1 -U postgres -v ON_ERROR_STOP=1 -v dbname=soltex \
     -v migrate_password=<local> -v app_password=<local> -v backup_password=<local> \
     -f apps/api/db/provision.sql
```

Put the three URLs in your local environment (see `.env.example`), then run `npm run db:migrate && npm run db:import`. `npm run test:db` resets the content tables of the database it points to and creates test users, so use a separate local database for it.
